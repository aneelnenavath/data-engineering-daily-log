# Day 14 — PySpark Aggregation

A PySpark script that groups and aggregates a CSV and writes the result
as Parquet, with the output re-read back from disk afterward to confirm
it's genuinely there — not just that the script exited without error.

## What it does (`pyspark_aggregation.py`)

1. Reads `sales_data.csv` (313 synthetic orders across 6 products,
   generated by `generate_data.py` with a fixed random seed).
2. Groups by `product_name`, computing total revenue, order count, and
   average order value per product.
3. Writes the aggregated result to `product_revenue_parquet/`.
4. Re-reads that Parquet directory back and re-prints it, to prove the
   write genuinely landed on disk rather than trusting a clean exit code.

## Two real Windows/Hadoop setup issues, not code bugs

PySpark bundles Hadoop's Java client libraries even for pure local-mode
file I/O with no real HDFS involved, and Hadoop on Windows needs two
extra native pieces that Linux doesn't:

1. **`winutils.exe` missing** — first run failed immediately during
   Spark's own startup with `HADOOP_HOME and hadoop.home.dir are unset`.
   Hadoop's `Shell` class uses `winutils.exe` as a Windows shim for
   file-permission operations it would otherwise do natively on Linux.
   Fixed by downloading `winutils.exe` into `C:\hadoop\bin` and setting
   `HADOOP_HOME=C:\hadoop`.
2. **`hadoop.dll` missing** — with `winutils.exe` in place, Spark got
   much further (CSV read and aggregation both worked), but the actual
   Parquet *write* failed during its final commit step with
   `UnsatisfiedLinkError: NativeIO$Windows.access0`. `winutils.exe` is
   just the executable shim; some native file-access checks are
   implemented in a separate JNI library, `hadoop.dll`, which has to sit
   alongside it. Fixed by downloading `hadoop.dll` into the same
   `C:\hadoop\bin` folder already on `PATH`.

## Verification

- The aggregated table read directly after the `groupBy` and the same
  table re-read from the Parquet files on disk match exactly.
- `num_orders` across all 6 products sums to 313 — exactly the row count
  `generate_data.py` reported writing, confirming no rows were dropped
  or double-counted during aggregation.
- `ls -la product_revenue_parquet/` shows a real `part-00000-*.snappy.parquet`
  file and a `_SUCCESS` marker, not just an empty directory.
