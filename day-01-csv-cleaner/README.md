# Day 1 — CSV Data Cleaner

**Stack:** Python, pandas

## Task

Take a messy CSV of customer signups and produce a clean version, with a log of
exactly what was fixed and why. "Messy" here means the three most common real-world
problems: missing values, duplicate rows, and inconsistent text casing.

## Files

- `messy_customers.csv` — the raw input. 15 rows, deliberately broken in a few ways
  (see below).
- `clean_csv.py` — the cleaning script. Run it with `python3 clean_csv.py`.
- `cleaned_customers.csv` — the output: 10 clean rows.
- `fix_log.txt` — a plain-text log of every fix, generated by the script (not written
  by hand), so the cleaning is reproducible and auditable.

## What's wrong with the input, and how each problem was handled

| Problem | Example | Fix |
|---|---|---|
| Inconsistent casing | `London`, `LONDON`, `london` all appear as city values | Title-case every city, lowercase every email and plan_type, *before* deduplicating — otherwise casing differences would hide duplicates |
| Missing required fields | Row `1005` and `1012` have no email | Dropped. `customer_id`, `name`, and `email` are treated as required — a missing email can't be guessed, so the row is unusable |
| Missing recoverable fields | Row `1010` has no `signup_date`, row `1003` has no `plan_type` | Filled with the literal string `"unknown"` rather than dropping the row — losing a whole customer record over one non-critical field is worse than flagging it |
| Exact duplicate rows | `1002` / `1004` (Bob Singh) are identical | Dropped, keeping the first occurrence |
| Near-duplicates hidden by casing | `1001` / `1009` (Alice Turner, same city written identically after normalising) and `1013` / `1015` (Karen Wu, `Glasgow` vs `glasgow`) | Caught because de-duplication runs *after* text normalisation |

## Why this design (the questions an interviewer would ask)

- **Why drop rows instead of imputing the missing email?** An email is an identity
  field — inventing one would silently corrupt the data. A missing `city` is a
  data-quality issue; a missing `email` is a data-integrity issue. They get different
  treatment on purpose.
- **Why normalise before deduplicating?** `drop_duplicates()` compares values
  literally. `"London"` and `"LONDON"` are different strings to pandas even though
  they're the same fact. Normalise text first, or duplicates slip through.
- **Why exclude `customer_id` from the duplicate comparison?** Two rows can describe
  the same real-world signup event with different surrogate IDs (e.g. a retry that
  got re-inserted). Comparing on the business columns, not the ID column, is what
  actually catches that.
- **Why log to a file instead of just printing?** The log is the audit trail — for a
  real pipeline, someone (including future-me) needs to be able to answer "what did
  this run actually change?" without re-deriving it by diffing two CSVs by eye.

## How to run

```bash
python3 clean_csv.py
```

Reads `messy_customers.csv`, writes `cleaned_customers.csv` and `fix_log.txt` into
the same folder.
